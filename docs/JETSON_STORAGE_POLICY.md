# Jetson SQLite/storage policy — SOFTWARE VERIFIED, not SD-card durability evidence

Local file databases use SQLite WAL, busy_timeout=2000 ms, synchronous=FULL, wal_autocheckpoint=100 pages and journal_size_limit=4 MiB. Transactions and RLocks cover meaningful writes; ledger claims use BEGIN IMMEDIATE to serialize first-writer allocation. Tests exercise schema-v2 open/reopen, retention, atomic visits, errors and replay. WAL is not configured for memory DBs. No schema change is required for these PRAGMA settings.

Only events/confirmed sessions become durable records; predictions/images remain transient. Generic retention defaults 1,000 events; typed tables 10,000 rows per kind; feed ledger 10,000 rows then fails closed (no ID reuse). A failed visit write holds **one** pending visit for paced retry, then faults without reading more frames in a crash loop. Shutdown attempts to finish/close only after the owned observation worker stops. Unsaved state/fault remains visible; no actuator intent follows from a DB failure.

These settings do not guarantee SD-card flush/power-loss behavior. A long-running external reader can prevent WAL checkpoint/truncation; the journal size setting is not an absolute cap during active transactions. Queries are short/bounded in this service, but monitor real WAL/disk behavior and use an appropriate card/supply. Avoid per-frame writes, unbounded log redirection, repeated VACUUM on a card or copying a live DB file without SQLite backup.

`tools.storage_report` reports DB/WAL/SHM, known log/dataset sizes and free space without deletion; directory scans are bounded and report truncation. Dataset/video imports and backup/reset are explicit development actions, not daemon capture. Manual datasets/backups and OS temporary retention require an operator disk policy; nothing is silently deleted. Configure bounded journald/rotating logs separately. A very large existing SQLite file does not automatically shrink just because retention prunes rows.
